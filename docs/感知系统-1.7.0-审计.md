# 言语 1.7.0 感知系统独立审计

审计日期：2026-11-25  
范围：通知观察、前台应用、粗粒度网络位置、天气、SearXNG 搜索、Room v6、上下文注入、设置页  
结论：存在 1 个 P0、4 个 P1、5 个 P2。**当前版本不应直接作为“隐私承诺已完成”的正式版交付。**

## P0：Android 8/9 启动崩溃

位置：

- `android-app/app/src/main/java/com/xinyu/companion/ui/MainApp.kt:36`
- `android-app/app/src/main/java/com/xinyu/companion/data/perception/AndroidForegroundAppProvider.kt:57`

触发条件：

1. App 运行在 Android 8.0–9.0（API 26–28）。
2. 启动 `MainApp`。
3. `PerceptionViewModel` 构造时调用 `accessChecker.status()`。
4. `AndroidForegroundAppProvider.hasUsageAccess()` 调用
   `AppOpsManager.unsafeCheckOpNoThrow`。该方法从 API 29 才可用，而项目
   `minSdk = 26`。

影响：支持范围内的设备会在启动阶段抛 `NoSuchMethodError`，不只是感知设置页崩溃。

修复：

```kotlin
val mode = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
    appOps.unsafeCheckOpNoThrow(
        AppOpsManager.OPSTR_GET_USAGE_STATS,
        Process.myUid(),
        context.packageName,
    )
} else {
    appOps.checkOpNoThrow(
        AppOpsManager.OPSTR_GET_USAGE_STATS,
        Process.myUid(),
        context.packageName,
    )
}
```

必须增加 API 26/28 Robolectric 或 instrumentation 启动测试。

## P1：撤销通知权限后仍会使用旧观察

位置：

- `domain/perception/PerceptionContextCoordinator.kt:26`
- `domain/perception/PerceptionContextCoordinator.kt:28`
- `ui/perception/PerceptionViewModel.kt:115`

现状：

`PerceptionContextCoordinator` 只从 `notificationStore.activeEvents()` 取事件，不检查：

- 系统通知使用权当前是否仍开启。
- 事件来源包当前是否仍在允许列表。

用户执行任一操作后：

1. 在系统设置撤销“通知使用权”。
2. 在感知页关闭某个通知来源。

该来源过去 24–72 小时的事件仍可能被选中并发送给 DeepSeek。

修复：

- `PerceptionContextCoordinator` 注入 `PerceptionAccessChecker` 和
  `NotificationSourceSettings`。
- 通知使用权关闭时立即排除全部通知观察。
- 只保留 `sourcePackage in allowedPackages` 的事件。
- 关闭单个来源时，同时清除该来源已有事件，或在存储查询层硬过滤。

回归用例：关闭来源/撤销权限后，即使数据库里仍有事件，`build()` 的
`notifications` 必须为空。

## P1：联网搜索发送的是整句用户消息

位置：

- `domain/perception/PerceptionQueryPolicy.kt:38`
- `domain/perception/PerceptionContextCoordinator.kt:75`
- `domain/perception/PerceptionContextCoordinator.kt:82`

现状：

只要命中“查一下、最新、新闻”等词，就会把完整用户消息发送给用户配置的
SearXNG。当前敏感过滤只覆盖身份证、银行卡、密码、验证码、手机号和家庭住址，
无法覆盖：

- 人名。
- 学校、公司、精确事件。
- 情绪叙事。
- 邮箱、账号、订单号。
- 上下文里隐含的私人事实。

例：

```text
我今天在苏州和某人吵架了，帮我查一下晚上怎么放松
```

整句可能被发送到搜索服务。

修复选择，按优先级：

1. 搜索前生成仅含检索实体的短查询，例如“晚上放松方法”，并在 UI 显示。
2. 含第一人称私人叙事的消息，不自动搜索，等用户点击“联网查”。
3. 搜索前确认并允许用户编辑查询词。

测试必须验证个人叙事不会原样进入 `WebSearchProvider.search`。

## P1：通用通知持有过宽且可进入云端上下文

位置：

- `data/notification/NotificationParser.kt:27`
- `data/notification/NotificationParser.kt:73`
- `data/notification/NotificationTextSanitizer.kt:31`
- `domain/perception/PerceptionContextCoordinator.kt:28`

现状：

用户允许某个应用后，除少量正则命中的敏感内容外，所有通知都可能作为
`GENERIC` 保存 24 小时。清洗器没有覆盖姓名、邮箱、订单号、账户尾号、
普通会议信息等。只要当前消息和摘要存在词面重叠，摘要就可能被注入并发送给
DeepSeek。

影响：用户同意“允许菜鸟”不等于同意该应用所有通知正文都可进入云端模型。

修复：

- 首版只持久化 `PARCEL_READY`、`COURSE_UPDATE`、`CALENDAR_UPDATE`。
- 增加独立开关“允许普通通知摘要”，默认关闭。
- 默认不保存 `GENERIC`；本地 UI 只展示事件类型，不展示任意正文。

## P1：中文验证码正则存在漏网

位置：

- `data/notification/NotificationTextSanitizer.kt:11`

现状：

`standaloneOtpPattern` 依赖 `\b`：

```regex
\b\d{4,8}\b(?=\s*(?:为|是|验证码|校验码))
```

中文与数字都属于正则 word 字符，`123456是验证码` 中数字和“是”之间通常没有
`\b` 边界，因此可能不被识别。若同时没有“验证码 123456”这种前置格式，纯
验证码通知可能被判为 `NORMAL` 并进入普通事件。

修复：

```regex
(?<!\d)\d{4,8}(?!\d)(?=\s*(?:为|是|验证码|校验码))
```

增加 `123456是验证码`、`你的验证码为123456`、带空格和中文标点等测试。

## P1：通知异步任务没有失败隔离

位置：

- `data/notification/NotificationIntake.kt:36`

现状：

`scope.launch { process(...) }` 没有异常边界。数据库锁定、磁盘错误、Keystore
异常等可能把未捕获异常交给 Android 默认处理器，导致通知进程崩溃。

修复：

```kotlin
scope.launch {
    runCatching { process(...) }
        .onFailure { /* 结构化诊断，不记录通知正文 */ }
}
```

只记录包名哈希、错误类型和重试情况，不记录标题、正文或数据库参数。

## P2：外部字段未全部转义

位置：

- `domain/CompanionPromptBuilder.kt:31`
- `domain/CompanionPromptBuilder.kt:34`
- `domain/CompanionPromptBuilder.kt:39`

通知摘要和搜索结果已经转义，但网络城市、前台应用标签、天气 `conciseText()`
仍未转义。应用标签或天气位置文本即使概率低，也可能包含 `<`、`>`，破坏
`live_context` 边界。

修复：所有进入 `<live_context>` 的外部字符串统一调用 `escapePromptData()`。

## P2：搜索“成功但零结果”仍被当作成功

位置：

- `domain/perception/PerceptionContextCoordinator.kt:80`
- `domain/ChatEngine.kt:325`

现状：

SearXNG 返回合法空列表时，`context.search != null`，聊天会显示
“已联网搜索 0 个来源”，模型仍收到搜索区。用户可能误以为已核实。

修复：

- 空结果转成 note：“没有找到可用搜索结果”。
- `search = null`，状态显示“未找到来源”，并明确禁止声称已核实。

## P2：来源列表与模型引用没有绑定

位置：

- `domain/ChatEngine.kt:332`

现状：

回答生成后，代码会把所有未在回答文本中出现的搜索 URL 追加到“参考来源”。
这不证明模型使用了这些来源，也可能把无关结果展示为用户答案的依据。

修复：

- 让模型只输出 `[S1]` 这类内部引用标记。
- App 只根据实际出现的标记渲染来源。
- 未引用结果不附加。

## P2：前台应用可能过期

位置：

- `data/perception/AndroidForegroundAppProvider.kt:26`
- `data/perception/AndroidForegroundAppProvider.kt:34`

现状：

只扫描最近 10 分钟的 `ACTIVITY_RESUMED`，忽略后续 `ACTIVITY_PAUSED`/
`ACTIVITY_STOPPED`。用户 9 分钟前离开的应用仍可能被描述为“现在正在使用”。

修复：

- 同时追踪 pause/stop 事件，只接受最新事件为 resumed 的应用。
- 把有效期缩短到 1–2 分钟。
- Prompt 中明确写“最近一次观测”，不要写“正在使用”。

## P2：网络城市缓存没有绑定网络身份

位置：

- `data/perception/CoarseNetworkLocationProvider.kt:37`
- `data/perception/CoarseNetworkLocationProvider.kt:60`

现状：

城市缓存 6 小时；从 Wi-Fi 切换到移动网络时只更新 `networkType`，城市仍旧。
可能导致天气查询使用旧城市。

修复：缓存键加入 network handle/transport 和 Wi-Fi 网络标识；网络变化时清除缓存。

## P2：搜索/天气响应先完整读入内存再检查大小

位置：

- `data/search/SearxngWebSearchProvider.kt:71`
- `data/search/OpenMeteoWeatherProvider.kt:108`
- `data/perception/CoarseNetworkLocationProvider.kt:58`

对于未知 `Content-Length` 或 chunked 响应，`body.string()` 会先完整读入，
再检查字符数。恶意或被劫持的服务可造成短时内存压力。

修复：按字节上限流式读取，超限立即中止；不要先构造完整字符串。

## 值得保留的设计

- 通知来源默认全部拒绝。
- 未允许来源只记录包名和最近出现时间，不保存正文。
- 通知正文先清洗再结构化。
- 包裹事件不保留取餐/取件码。
- 搜索地址仅允许 HTTPS，拒绝账号密码和查询参数。
- 搜索结果 URL 拒绝 `javascript:`、`data:` 等伪协议。
- 搜索结果被标记为 `untrusted-data` 并限制字符数。
- 观察数据保存在同一 SQLCipher 数据库。
- 页面明确说明观察摘要可能发送给 DeepSeek。
- ChatEngine 允许环境读取失败时继续普通聊天。

## 测试覆盖现状与缺口

当前已通过：

- 通知清洗和解析单元测试。
- 搜索与天气 provider 专项测试。
- 感知查询策略与上下文协调器测试。
- Room 感知事件持久化测试。
- 数据库 v4→v5→v6 迁移测试。
- Compose 感知页面测试。
- 现有聊天与记忆回归。

尚缺：

1. API 26/28 启动测试（P0 回归）。
2. 撤销通知权限后旧事件不再进入 prompt。
3. 关闭单个来源后旧事件立即不可用。
4. 完整隐私叙事不会原样发送给 SearXNG。
5. 中文验证码边界测试。
6. 空搜索结果不宣称查询成功。
7. 搜索结果 prompt injection 的端到端测试。
8. 通知服务数据库异常不导致进程崩溃。
9. ChatEngine 获取到的 `PerceptionPromptContext` 与最终 system prompt 的集成断言。
10. 在 Android 14/15 真机上验证通知使用权、使用情况访问的授权与撤销。
