# 言语 1.4.0 架构审计与 1.6.0 记忆系统复审

初审日期：2026-11-23

最近复审：2026-11-24

审查目标：`android-app/`

辅助证据：`server/`、`contracts/`、项目文档和已安装的 10 个架构技能。

## 结论

以下为 1.4.0 初审时的问题记录。当前可运行版本已推进到 1.6.0，实际修复状态见下方各发现和复审报告。

1.4.0 可定义为：

> 个人自用、BYOK、Android 原生、单会话 AI 陪伴聊天盒。

这条路线可以继续走。聊天生命周期、Provider 抽象、本地加密、SSE 流式回复和数据库事务已经构成可用地基。

当前还不能直接作为开源源码仓库或公开运营产品交付。阻断项按优先级为：

1. 源码目录内存在 785.70 MB 的 JVM 堆转储，并检测到 6 处符合 API Key 形态的字符串。
2. 聊天页写着“仅保存在本机”，与真实上下文发送链路冲突。
3. `domain` 反向依赖 `data`，与项目文档宣称的依赖方向不一致。
4. 危机识别只有少量关键词匹配，存在明显漏判和误判。
5. 设置页、密钥存储、进程死亡和真实供应商调用缺少设备级验收。

判定：

- 作为自己手机上的 1.4.0 测试版：主体可用，但最新版尚未完成真机验收。
- 作为开源首发版：阻塞。
- 作为公开收费运营版：阻塞，需要服务端代理、账户、额度、计费、合规和运营体系。

## 主要问题

以下严重度按“公开发布口径”评定。个人自用测试版可以临时接受其中一部分风险，但开源或公开运营版本不能。

### P0：堆转储可能泄露真实凭据（1.5.0 已隔离）

严重度：CRITICAL  
置信度：10/10

证据：

- `android-app/java_pid28120.hprof` 大小为 785.70 MB。
- 文件头为 `JAVA PROFILE 1.0.2`。
- 扫描到 6 处符合 `sk-` API Key 形态的字符串。
- `.gitignore` 第 9 至 16 行没有排除 `*.hprof`。

影响：

- 当前仓库没有 commit，所有文件都未跟踪。一次 `git add .` 就可能把该文件带入历史。
- 即使随后删除文件，只要已经提交，凭据仍会留在 Git 历史。

建议：

1. 轮换该机器近期使用过的 DeepSeek Key。
2. 将 `*.hprof` 加入 `.gitignore`。
3. 确认无需保留后，再将转储移出源码目录。
4. 开源前扫描 Git 历史和整个工作目录。

本次审查没有打印匹配内容。1.5.0 已把文件移动到：

```text
D:\Users\Administrator\Documents\ChatGPT\heap-dumps\xinyu-java_pid28120.hprof
```

同时已加入 `*.hprof` 忽略规则。文件没有直接删除，仍可在隔离目录中确认。

### P0：隐私文案与实际数据流冲突（1.5.0 已修复）

严重度：CRITICAL  
置信度：10/10

证据：

- `ChatScreen.kt:243` 显示“私人对话 · 仅保存在本机”。
- 实际请求会把上下文发送到 `https://api.deepseek.com/chat/completions`。
- `ChatScreen.kt:273` 又说明“模型请求会发送到 DeepSeek”。

触发问题的原文：

```kotlin
if (hasApiKey) "私人对话 · 仅保存在本机" else "等待连接"
```

影响：用户可能把“仅保存在本机”理解为“从未离开手机”。对陪伴产品，隐私承诺是信任底座。

建议改成：

```text
记录加密保存在本机 · 本轮上下文会发送给 DeepSeek
```

正式版还应说明供应商的数据保留和训练政策以 DeepSeek 条款为准。

1.5.0 当前文案：

```text
记录加密保存在本机 · 本轮上下文会发送给 DeepSeek
```

### P1：领域层反向依赖数据层（1.5.0 已修复）

严重度：CRITICAL  
置信度：10/10

证据：

- `ChatEngine.kt:3-6` 直接导入 `data.provider`、`data.security`、`data.settings`。
- `ChatEngine.kt:42` 自己创建 `CoroutineScope(Dispatchers.Main.immediate)`。
- `docs/聊天内核架构.md` 画的是 `Domain → Adapters`，与实际依赖相反。

触发问题的原文：

### P1：危机安全策略覆盖不足（1.5.0 已增强，仍需真实回复评估）

严重度：CRITICAL  
置信度：9/10

证据：

- `SafetyPolicy.kt:12` 使用 `CRISIS_MARKERS.any(normalized::contains)`。
- `SafetyPolicy.kt:29-36` 只有少量中文和英文短语。
- `ChatScreen.kt:498` 只提供 120、身边人和泛称“专业心理援助”。

触发问题的原文：

```kotlin
val crisis = CRISIS_MARKERS.any(normalized::contains)
```

风险：

- “撑不下去了”“我想消失”“活着没意思”等表达可能漏判。
- “我不想自杀”这样的否定句会被误判。
- 对低情绪用户，不能只靠关键词决定是否暂停角色扮演。

建议：

- 先做高风险召回层，再让模型输出结构化紧迫程度。
- 高风险时停止普通角色扮演。
- 提供当前可用的心理援助热线，并同时给出 120、110 和联系可信任的人。
- 明确 AI 不能替代急救和现实支持。
- 增加否定句、隐喻、英文和混合表达的评估集。

1.5.0 已区分 `crisis`、`distress` 和 `normal`，增加否定判断、更多自伤意图与痛苦表达，以及 12356、120、110 等现实援助信息。真实模型回复质量仍未做线上评估。

### P2：数据库完整性约束不足（1.5.0 已修复）

严重度：INFORMATIONAL  
置信度：10/10

## UI 设置架构

当前用 `showSettings: Boolean` 在两页之间切换，对 1.4.0 足够。

保留现有设计：

- 全屏设置页。
- 首次无 Key 强制进入连接页。
- 聊天状态与设置草稿分开。
- 滑杆松手后自动保存。
- 删除 Key、清空聊天分别确认。

加入多会话时再改成明确路由：

```kotlin
sealed interface AppRoute {
    data object Bootstrap : AppRoute
    data object Chat : AppRoute
    data object Settings : AppRoute
    data object ConversationList : AppRoute
}
```

当设置继续增加角色、记忆、模型、导入导出时，再拆：

- `AppViewModel`：启动、连接状态、全局错误。
- `ChatViewModel`：当前会话和生成。
- `SettingsViewModel`：设置草稿和保存。

现在拆三个 ViewModel 会增加协调成本，不属于最小改动。

## Provider 契约

端口应放在领域层：

```kotlin
interface ChatProvider {
    val descriptor: ProviderDescriptor
    fun stream(request: ProviderRequest): Flow<GenerationEvent>
    suspend fun testConnection(config: ProviderConnection): Result<Unit>
}
```

约束：

- `domain` 不导入 OkHttp、Room、SharedPreferences 或 Hilt。
- 每个适配器把供应商 JSON 映射成统一错误码。
- `safetyInstruction` 只保留一个来源；当前在系统提示和 `ChatRequest` 中重复。
- `X-Client` 从 `BuildConfig.VERSION_NAME` 生成，不手写版本。

## 数据库演进

当前 Room + SQLCipher 是正确选择。多会话前先补完整性：

```text
conversations
  1 ── * messages
           └── replyToMessageId ──> messages.id

companions
  1 ── * conversations
  1 ── * memories
```

迁移原则：

1. 先增加外键和索引，不改现有消息内容。
2. 不复用已经发给用户的迁移编号。
3. 每次迁移同时保留 schema JSON、迁移测试和旧数据可读断言。
4. 消息列表按 `conversationId + sequence` 分页，不能永久一次加载全部历史。

## 公开运营后的边界

公开运营不能继续让每台手机持有平台供应商 Key。

```text
Android App
  └─ account access token
        ↓ HTTPS
Platform API
  ├─ account / auth
  ├─ quota / billing
  ├─ abuse prevention
  ├─ provider router
  └─ audit metadata
        ↓
DeepSeek / other providers
```

必须实现：

- 短期访问令牌和可撤销刷新令牌。
- 服务端 Secret Manager 保存供应商 Key。
- 按账号、设备、IP 和模型限流。
- 请求幂等键，防止重试造成重复扣费。
- 先预占额度，成功后按 usage 结算，失败时释放。
- 日志默认不记录聊天正文。
- 未成年人保护、隐私政策、供应商条款和内容边界。

“预占额度 → 调用模型 → 结算或释放”是未来收费版的小型 Saga。当前单机版本不需要 Saga。

- 冷启动到可操作界面：目标小于 2 秒。
- 普通设备数据库查询：p95 小于 50 ms。
- 崩溃后最多丢失最后约 450 ms 的流式文本。
- Key 不得出现在普通日志、崩溃报告或仓库。

公开版：

- API 月可用性目标先定 99.9%。
- 元数据与计费数据 RPO 小于 5 分钟，RTO 小于 1 小时。
- 聊天正文默认本地保存；服务端若确需保存，必须单独取得明确同意。

## 失败模式

| 失败 | 当前行为 | 目标 |
| --- | --- | --- |
| 手机断网 | 显示网络错误，可重试 | 保留 |
| SSE 提前结束 | 标为失败，可重试 | 保留并记录错误码 |
| App 被杀 | 半截回复标为中断 | 增加真机测试 |
| Keystore 解密失败 | Key 视为空，要求重填 | 增加明确恢复入口 |
| SQLCipher 载入失败 | 启动错误页 | 增加数据库打开失败页 |
| 数据库写终态失败 | 显示持久化错误 | 单独错误码和恢复动作 |
| 供应商返回流内错误 | 可能被解析器吞掉 | 映射统一错误事件 |
| 危机关键词漏判 | 普通角色继续回复 | 多层安全识别 |

## ADR 摘要

### ADR-001：继续采用 Android 原生模块化单体

状态：Accepted

理由：单团队、单端、低运维成本，当前没有独立扩展和独立部署需求。

拒绝：React/Capacitor 套壳、微服务、Kubernetes。

### ADR-002：个人版使用 BYOK 直连

状态：Accepted for personal mode

理由：没有平台账户和扣费时，手机直连供应商是最小可行方案。

限制：不能据此推导公开运营版。公开运营版必须使用服务端代理。

### ADR-003：领域层定义端口，数据层实现端口

状态：Proposed

理由：兑现“切换 DeepSeek、OpenAI、Ollama 不需要重写上层”的目标。

### ADR-004：本地聊天数据优先

状态：Accepted

理由：陪伴对话敏感，Room + SQLCipher 是当前合理默认。

后续：公开版需提供加密导出、清除和数据保留说明。

### ADR-005：当前不引入 Saga、消息队列和云基础设施

状态：Accepted

理由：单机单事务不构成跨服务事务。

升级触发：出现账户中心、充值扣费、异步任务和多服务调用时再引入。
